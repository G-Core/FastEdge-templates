# Generation Config — FastEdge-templates

> **What this file is**: instructions for keeping the doc files listed in `manifest.json` current.
> **Who reads this**: template maintainers (human or agent). The plugin pipeline does NOT read this file.
> There is no `generate-docs.sh` here — unlike SDK repos, these docs are hand-authored product
> documentation, not extracted from source code. Keep them accurate by hand.

## When you add a new template directory

1. Add its `README.md` to the `catalog` source's `files` array in `manifest.json`.
2. If the template requires the customer to write or change code in their own origin (not just
   set env vars), write a `context/integration.md` (or `context/design/integration.md`) documenting
   the contract — routes, request/response shapes, shared secrets/keys, and any code snippets a
   customer would paste into their own codebase. Add a new `<template>-integration` source entry
   pointing at it, plus a `target_mapping` entry under
   `plugins/gcore-fastedge/skills/fastedge-docs/reference/templates/<template>-integration.md`.
3. If the template is config-only (env vars, no origin code — e.g. `harden-cookies`, `html2md`),
   skip step 2. The catalog entry alone is enough for the plugin to recommend it.
4. `.github/workflows/validate-plugin-contract.yml` fails the PR if a directory containing a
   `registry.json` isn't referenced anywhere in `manifest.json` — this is what forces step 1 to
   actually happen when a template is added.

## What `README.md` (catalog source) must cover

Per template, in the root `README.md`'s template table and each template's own `README.md`:
- What problem it solves, in one sentence a developer would recognize before deciding to hand-build
  the same thing themselves (e.g. "adds SSO to any existing site without changing the backend").
- What FastEdge app type(s) it deploys as (HTTP app / CDN Proxy-WASM / both).
- Any runtime variant/mode selection (e.g. `SSO_VARIANT`) and what each mode means.

## What `context/integration.md` must cover, when it exists

- Every route/endpoint the customer's origin or browser can call, with method and purpose.
- Exact request/response JSON contracts for any endpoint a custom UI would call.
- Every shared secret/key between the template's apps and the customer's origin, and which side
  holds which half (symmetric secret vs. public-key-only via JWKS).
- Copy-pasteable snippets for the common integration paths (static links, dynamic widget, proof
  verification), not just prose description.
- Security notes that are load-bearing for a correct integration (e.g. redirect validation,
  origin-lock requirements) — a customer skipping these can ship a bypassable gate.

## Quality bar

Same standard as the rest of the ecosystem's `docs/`: technical prose, no marketing language,
runnable/copy-pasteable snippets, tables for structured data. See
`fastedge-plugin/scripts/sync/templates/generation-config-template.md` for the full style rules
the plugin pipeline's generator expects.
